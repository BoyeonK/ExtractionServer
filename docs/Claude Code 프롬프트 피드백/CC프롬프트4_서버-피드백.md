# CC프롬프트4_서버 피드백

50개. 클라 배치보다 짧지만 밀도가 높다. 성격도 다르다 — 클라 쪽이 구현·마감 작업이었다면 이쪽은 거의 전부 **설계 대화**라, 다른 종류의 문제가 드러난다.

---

## 이번 배치의 최고 순간

두 개인데, 둘 다 앞서 지적했던 것을 스스로 넘어선 경우다.

### 1. 설계를 폐기하고 처음으로 되돌린 것

> "클라이언트측의 요구사항에 맞추어서 빙 돌아가는 느낌이 조금 들어. 처음으로 돌아가서 다시 설계하려고 해."

"제안-반박 구조는 국소 최적화만 가능하다"고 지적했던 부분이다. 제안에 대한 반박을 받는 방식으로는 **프레임 자체가 틀렸다는 신호가 안 나온다.** 그런데 여기서는 누적된 굴절을 스스로 감지하고 리셋했다. 그 직후 다시 세운 3단계 설계(버전 불일치 → 싱크만, 일치 → 장전 후 통보)가 훨씬 단순하다.

### 2. 문서 취사 기준

> "'이 문장이 없으면 다음 세션이 코드를 잘못 고치는가?' 를 조건으로서 남길 말과 남기지 않을 말을 가르려고 해."

앞서 제안했던 건 금지 항목 **목록**이었는데, 이건 **판정 기준**이다. 목록은 열거한 것만 걸러내고, 기준은 열거하지 않은 경우까지 처리한다. 이쪽이 낫다. 문서 규칙 초안의 금지 항목들은 이 한 문장으로 대체하는 것이 맞다.

### 부수적으로 좋았던 것

- **낙관적 전제를 그렇게 명명한 것** — "올바른 탄창이 들어가도록 설계되었다는 낙관적 기대를 바탕으로". 전제를 낙관적이라고 이름 붙여두면 나중에 깨질 지점이 표시된다.
- **반박을 받고 더 멀리 간 것** — 스푸핑 지적을 받자 검증을 강화하는 대신 `object_id` 필드 자체를 제거.
- **정보 은닉 결정 두 건** — killer 미해결 시 빈 문자열, DB 구조를 git에 노출하지 않기. LLM은 진단 정보를 늘리는 방향을 기본으로 제안하는데, 그게 공개 서버에서는 반대로 작동한다.

## 최대 문제: 클라이언트 요구사항이 원문 그대로 유입됐다

> "현재 장전 로직에서 클라이언트의 요구사항이 있어. 응답에 "어느 무기의 탄창인지"가 없다. magazine은 InventorySlot 한 개뿐이고 주/보조 구분 필드가 없어, 클라가 수신 시점의 IsPrimaryWeaponApplyed로 추정해야 한다. 요청과 응답 사이에 무기 교체가 확정되면 반대쪽 슬롯에 써넣는다. ... — 서버에 물어볼 1순위."

클라 세션의 출력을 그대로 붙인 것인데, 여기에는 **클라이언트 내부 사정이 섞여 있다.** `IsPrimaryWeaponApplyed`라는 클라이언트 변수명, 수신 시점 추정 로직, 클라 세션이 매긴 우선순위 라벨까지.

그 뒤에 벌어진 일:

1. 서버 설계가 "클라이언트가 추정에 실패하지 않게 하려면"을 축으로 잡음
2. 델타를 보낼지 스냅샷을 보낼지, MTU를 넘는지, 청킹이 필요한지로 논의가 번짐
3. `blueprint_id == 0`이 빈 칸을 의미하는지 같은 규약 문제까지 파생
4. **"빙 돌아가는 느낌" → 폐기 후 재설계**

리셋 후의 결론은 인벤토리 버전 기반 동기화였고, 이건 클라이언트가 어떻게 추정하든 무관한 설계다. **처음부터 인터페이스 수준의 요구로 번역해서 넘겼다면** 이 우회가 없었다.

원문 대신 이 한 줄이면 충분했다.

```
클라이언트 요구: D2CResponseReload 응답에 어느 무기 슬롯의 탄창인지
구분할 수단이 필요해. 현재는 없어서 클라이언트가 추정해야 하는 상황이야.
```

같은 로그 뒤쪽에서 세션 경계 규칙을 세웠는데, **그 규칙이 막으려는 것이 정확히 이 유입이다.** 다만 규칙은 "코드를 읽지 않는다"만 다루고 **전달되는 텍스트**는 다루지 않는다. 반대편 세션의 출력을 붙여넣는 것도 같은 오염 경로다.

규칙에 추가할 것:

```
반대편 세션의 출력을 그대로 옮기지 않는다. 요구사항은 인터페이스 수준
(어떤 패킷에 어떤 정보가 필요한가)으로 번역해서 전달한다.
반대편의 내부 변수명이나 구현 방식은 전달하지 않는다.
```

## 세션 경계 규칙에 구멍이 있다

실제로 보낸 규칙에서 `.proto` 예외 조항이 빠졌다.

> "클라이언트 디렉터리(Extraction/Extraction/)의 코드는 읽지 않는다. 수정뿐 아니라 열람도 하지 않는다."

그런데 바로 다음에:

> "클라이언트 세션 측에서 작업 완료된 내용을 바탕으로 External_Protocol.proto파일의 주석을 정리했어 해당 내용을 추적하고..."

`.proto`의 원본이 클라이언트 쪽에 있고(빌드 전에 서버로 복사하는 구조), 곧 클라이언트 파일로 대체될 예정이기도 하다. **규칙대로면 서버 세션이 그 파일을 열 수 없다.** 지금은 세션이 알아서 예외 취급하고 있지만, 다음 세션에서 규칙을 곧이곧대로 적용하면 막힌다.

명시적으로 넣어야 한다. `.proto` 수정 권한을 어느 쪽이 갖는지도 여전히 미정이다 — 이번 배치에서도 "클라이언트 파일로 대체될 예정"이라는 말만 있고 결정은 없다.

## 생성물에 수정 금지 표시가 빠졌다

> "빌드를 진행하기 전에 ./database/ItemDataManager.h 파일을 ./src/DedicateProcess/ItemDataManager.h에 덮어쓰고 싶어."

이 순간부터 `src/DedicateProcess/ItemDataManager.h`는 **매 빌드마다 덮어써지는 생성물**이다. 세션이 여기를 직접 고치면 다음 빌드에서 조용히 사라지고, 이 손실은 알아채기 어렵다.

클라 쪽 `ItemDBHelper.cs`에는 같은 처리를 했는데(수정 금지를 CLAUDE.md에 추가) 여기선 빠졌다. CMake 수정과 함께 나가야 할 지시다.

```
이 덮어쓰기 대상 파일은 빌드마다 생성되므로 직접 수정하지 않는다는 내용을
서버 CLAUDE.md와 파일 상단에 추가해줘. 원본은 ./database/ 쪽이야.
```

## 사소한 것

### `반론이 없다면 계획을 세워줘` (2회)

편의성은 있는데, 반론이 **하나만** 있을 때 어떻게 되는지가 불분명하다. 계획을 세우면서 각주로 달지, 멈추고 물을지가 정해져 있지 않다.

```
반론이 있으면 계획보다 먼저 제시해줘. 없으면 바로 계획으로 넘어가.
```

### `현재까지 설계 중에 결함이 있는 부분이 있을까?`

열린 질문이라 좋지만 근거 하한선이 없다. 실제로 돌아온 항목 중 하나("조용한 열기 실패")를 정상 동작으로 기각했다. `재현 시나리오를 구체적으로 못 대면 없다고 답해줘`를 붙이면 그 기각 턴이 줄어든다.

### 규칙을 거절할 때 이유가 없다

> "'클라이언트 작업 지시를 `.proto`에 적지 않는다' 라고 명시적으로 적고 싶지 않아."

이유가 없으면 다음 세션에서 같은 제안이 다시 올라온다. 실제로는 `.proto` 주석을 인계 채널로 쓰기로 했기 때문에 거절한 것일 텐데, 그 한 줄이 붙어야 결정이 남는다.

## 정리

설계 대화의 질은 이미 높고 두 번의 자기 교정(리셋, 문서 기준)이 그 증거다. 남은 비용은 전부 **두 세션의 접점** — 요구사항 번역, `.proto` 소유권, 생성물 표시 — 에 몰려 있다.
