Claude Code 프롬프트 개선사항 정리
=====================================

1. 컨텍스트 부족 — "변화가 있었어. 확인해줘"
---------------------------------------------
문제: Claude가 파일을 직접 읽어야 하므로 불필요한 토큰 소비 발생.
개선: 어떤 변화가 있었는지 핵심을 직접 언급한다.

  변경 전: "External_Protocol.proto에 변화 사항이 있었어. 해당 변화 내용을 확인해줘."
  변경 후: "External_Protocol.proto에 PlayerState 메시지에 action_state 필드가 추가되었어. 이에 따라 서버/클라이언트 코드를 수정하려고 해."


2. "계획을 세워줘" 남발
------------------------
문제: 이미 방향이 확실한 경우에도 계획 수립을 요청하면 실제 구현까지 왕복이 2배로 늘어남.
개선: 불확실할 때만 계획을 요청하고, 확실한 건 바로 구현을 요청한다.

  불확실할 때: "~하려고 해. 계획을 세워줘" (유지)
  확실할 때:   "~하려고 해. 진행해줘" (왕복 제거)


3. 점진적 소출 — 한 번에 줄 수 있는 정보를 나눠서 제공
-------------------------------------------------------
문제: 이미 확정된 스펙을 여러 턴에 나누어 제공하면 컨텍스트 효율과 결과 일관성이 떨어짐.
개선: 확정된 스펙은 하나의 프롬프트에 모두 담아서 보낸다.

  변경 전:
    턴 1: "6가지가 있으며 차례대로 알려줄게."
    턴 2: "먼저 inventorySlot에서 weaponSlot으로..."
    턴 3: "두번째로 weaponSlot에서 inventorySlot으로..."
    ...

  변경 후:
    턴 1: "6가지 메서드의 스펙은 다음과 같아. 1. ... 2. ... 3. ... 진행해줘."


4. "타당성을 검증해줘"의 표현 개선
-----------------------------------
문제: "타당성 검증"이라는 표현은 Claude가 찬성/반대 논증을 모두 펼치게 하여 토큰 소비가 큼.
      실제 의도는 "더 나은 대안이 있는지 확인"하는 것.
개선: 질문의 초점을 대안 탐색으로 옮긴다.

  변경 전: "~하려고 해. 타당성을 검증해줘."
  변경 후: "~하려고 해. 더 나은 방법이 있으면 제안해줘, 없으면 바로 진행해줘."
           "~로 진행할건데, 놓친 부분이 있으면 지적해줘."
           "~로 갈 건데 반론이 있어?"

  핵심: "없으면 바로 진행해줘"를 붙이면 대안이 없을 때 곧바로 구현으로 넘어감.


5. 모호한 짧은 응답
--------------------
문제: "r", "좋아 진행해줘" (무엇을?), "2번, 3번은 타당하다고 생각해" (이전 대화 없이는 의미 불명)
     새 세션에서 이런 패턴을 쓰면 Claude가 맥락을 잃어 오해할 수 있음.
개선: 최소한의 맥락을 포함하여 지시한다.

  변경 전: "좋아 진행해줘"
  변경 후: "좋아 FindNonplayerObject 분리 작업 진행해줘"


6. 빈 함수 생성 -> 내용 채우기 패턴
-------------------------------------
판단: 구현 스펙이 미확정 상태에서 함수 시그니처를 먼저 확보하는 전략은 타당함. 현행 유지 가능.
개선: 빈 함수 요청 시 대략적인 방향을 메모처럼 남겨두면 다음 턴에서 맥락 파악이 빨라짐.

  변경 전: "Handle_D2CUpdatePlayerStates 핸들러 함수를 일단 빈 함수로서 구현해줘."
  변경 후: "Handle_D2CUpdatePlayerStates 핸들러 함수를 빈 함수로서 구현해줘.
            이후에 OppoPlayerController에 상태를 할당하는 방향으로 채울 예정이야."

  효과: 함수 시그니처(매개변수 타입 등)를 더 정확하게 설계할 수 있고,
        이후 구현 턴에서의 수정도 줄어듦.


유지해야 할 좋은 패턴
======================
- 선택지를 번호로 제시하고 판단을 요청 (효과적인 의사결정 유도)
- 설계 의도와 이유를 함께 설명 (Claude가 맥락을 이해하고 더 나은 판단 가능)
- 단계적 구현 순서를 명시 ("먼저 ~에 집중, 나중에 해결" - 스코프 관리에 좋음)
- "이에 대해 어떻게 생각해"로 열린 피드백 요청
