# 문서 갈무리

비대해진 프로젝트 문서를 정리한다. **정보 손실 위험이 있는 작업이므로 각 단계에서 요구되는 승인 게이트를 건너뛰지 않는다.**

## 절대 규칙

- 게이트에서 승인 없이 다음 단계로 넘어가지 않는다
- 판단 근거가 부족하면 임의로 정리하지 않고 보고한다
- 정보를 옮길 때는 **새 위치에 먼저 반영한 뒤** 기존 위치를 줄인다
- 기능 변경과 섞지 않는다 (문서 정리 전용 커밋)
- **동작하는 코드는 변경하지 않는다** (주석 수정은 가능)

---

## 0단계. 착수 전 확인

git 상태를 확인한다. 미커밋 변경이 있으면 정리 범위와 겹치는지 판단한다.

```
미커밋 변경 발견
 ├─ 정리 범위와 겹침, 또는 diff를 분리할 수 없음
 │    → 중단하고 보고 (커밋하거나 stash한 뒤 다시 실행하도록 안내)
 └─ 무관함
      → GATE 1에서 함께 보고하고, 해당 파일은 건드리지 않는다
```

정리 diff가 다른 작업과 섞이면 리뷰와 되돌리기가 어려워진다.

---

## 1단계. 현황 파악

읽기만 한다. **파일을 수정하지 않는다.**

1. Bootstrap 문서(`CLAUDE.md`, `AGENTS.md` 등)를 읽어 문서 구조를 파악
2. 문서 인벤토리 작성 — 경로 / 역할 / 줄 수
3. 아래 신호로 문제 지점 식별

### 정리가 필요하다는 신호

**역할이 겹침**
- Bootstrap이 특정 컴포넌트 세부사항을 흡수함
- 한 문서가 현재 설계·과거 결정·작업 상태를 동시에 담당함
- 코드 주석이 과거 논의와 기각된 대안으로 길어짐

**무엇이 현재 사실인지 흐려짐**
- 현재 동작과 과거 결정 이유가 뒤섞임
- 같은 설명이 여러 위치에서 서로 다르게 변함
- 코드와 문서의 불일치가 반복됨
- 오래된 TODO나 Open Question이 남아 있음

**문맥 탐색 비용이 커짐**
- 관련 내용을 찾으려 여러 문서를 반복 탐색해야 함
- 깊은 문서를 읽어야만 현재 invariant를 알 수 있음

### 코드 탐색 범위

**저장소 전체를 선제적으로 스캔하지 않는다.** 1단계는 문서 인벤토리가 중심이다.

소스 코드를 읽는 것은 다음 두 경우로 한정한다.

- 분류 결과 local contract / invariant를 코드 가까이로 옮겨야 할 때 → 해당 구현 범위만
- 문서와 코드의 불일치를 확인해야 할 때 → 관련 범위만

주석 수정은 정리 범위에 포함할 수 있다. **동작하는 코드는 변경하지 않는다.**

---

## ■ GATE 1 — 범위 합의

**여기서 멈춘다.** 다음을 보고하고 승인을 기다린다.

```
## 문서 인벤토리
| 경로 | 역할 | 줄 수 |

## 발견된 신호
- [파일]: [어떤 신호] — [구체적 근거]

## 제안 범위
이번에 다룰 것: ...
이번에 다루지 않을 것: ...
```

한 번에 너무 많은 역할의 문서를 동시에 재구성하지 않는다. 범위는 좁게 제안한다.

**승인 없이 2단계로 넘어가지 않는다.**

---

## 2단계. 분류

승인된 범위 안에서만 작업한다.

각 정보를 **의미 단위**로 식별한다. 문서 전체나 문장 하나가 아니라, 하나의 contract·invariant·decision·rationale처럼 독립적으로 의미를 갖는 덩어리다.

한 블록에 여러 역할이 섞여 있으면 먼저 분해한다.

분류 기준과 각 목적지의 상세 역할은 `reference/classification.md`를 읽는다.

### 분류 결과

각 의미 단위를 다음 중 하나로 결정한다.

**KEEP** — 현재 위치에 유지. 더 할 일 없음.

**RELOCATE** — 다른 위치로 옮김.
- 목적지가 이미 있으면 → 3단계
- 목적지 신설이 필요하면 → GATE 2

**REMOVE / REDUCE** — 다른 위치에 보존할 필요가 없는 삭제/축약 후보.
- 3단계를 거치지 않고 **GATE 3의 승인 대상에 포함**한다
- 삭제하려는 정보를 위해 목적지를 만들지 않는다

**UNRESOLVED** — 근거가 부족함. 임의로 진행하지 않고 보고한다.

```
Semantic Unit
     │
     ├─ KEEP ──────────────→ 그대로
     │
     ├─ RELOCATE
     │     ├─ 목적지 있음 → 3단계 → GATE 3
     │     └─ 목적지 없음 → GATE 2 → 3단계 → GATE 3
     │
     ├─ REMOVE / REDUCE ───→ GATE 3
     │
     └─ UNRESOLVED ────────→ 보고 / 중단
```

---

## ■ GATE 2 — 목적지 신설

**새 파일이나 디렉터리가 필요하면 여기서 멈춘다.**

기존 문서 안에 새 섹션을 만드는 것은 GATE 1의 범위 승인에 포함된 것으로 본다. 이 게이트는 저장소 구조가 바뀌는 경우만 다룬다.

```
## 신설이 필요한 목적지
| 경로 | 이유 | 들어갈 내용 |

## 기존 문서로 대체 가능한지 검토한 결과
...
```

"옮길 곳이 필요하다"는 이유만으로 새 문서를 만들지 않는다. 기존 문서나 섹션으로 충분하면 그쪽을 쓴다.

**승인 없이 파일이나 디렉터리를 생성하지 않는다.**

---

## 3단계. 이동 (복사까지만)

**`RELOCATE`로 분류된 것만 다룬다.** `REMOVE / REDUCE`는 이 단계를 건너뛰고 GATE 3으로 간다.

승인된 목적지에 내용을 **복사하거나 다시 쓴다.**

**이 단계에서 기존 위치를 건드리지 않는다.** 원본은 그대로 둔다.

복사 후 검증한다.

- 중요한 contract가 빠지지 않았는가
- invariant가 의미상 보존되었는가
- reference가 올바른가
- 새 위치만 읽어도 그 문서 역할 안에서 이해 가능한가

절차 상세는 `reference/procedures.md`를 읽는다.

---

## ■ GATE 3 — 삭제/축약 승인

**기존 내용을 삭제하거나 줄이기 전 마지막 승인 지점이다. 여기서 멈춘다.**

이번 작업에서 처리한 것 전부를 한 번에 보고한다.

```
## 처리 결과
| 내용 | 원래 위치 | 분류 | 새 위치 | 최종 조치 |
|      |           | RELOCATE | ... | 삭제 / 축약 |
|      |           | REMOVE   |  -  | 삭제 |

## 삭제 후 탐색 경로 확인
[기존 위치를 지워도 필요한 정보를 찾아갈 수 있는지]

## 보류 항목 (있으면)
| 내용 | 위치 | 판단이 막힌 이유 |
```

**승인 없이 기존 내용을 삭제하거나 줄이지 않는다.**

---

## 4단계. 정리 완료

승인받은 대로 기존 위치를 삭제하거나 축약한다.

그다음 확인한다.

- Bootstrap에서 새 문서로 가는 경로가 연결되었는가
- 끊긴 참조가 없는가
- diff만 보고 무엇이 어디로 갔는지 추적 가능한가

저장소에 문서 검증 도구가 있으면 실행한다 — Markdown lint, link checker, doc build 등. Bootstrap이나 CI 설정에서 확인할 수 있다. 실패하면 고치고, 원인을 모르면 보고한다.

마지막으로 커밋 메시지를 제안한다. **실제 커밋은 하지 않는다.**

---

## 판단이 막혔을 때

다음 경우 임의로 진행하지 않고 보고한다.

- 문서와 코드가 충돌하는데 어느 쪽이 맞는지 확정할 수 없음
- 삭제 시 정보 손실 여부가 불명확함
- 범위 밖의 문제를 발견함
- 이 문서의 기준으로 분류되지 않는 정보를 만남

애매함 자체는 문제가 아니다. **근거 없이 정보 손실 가능성이 있는 판단을 내리는 것**이 문제다.
