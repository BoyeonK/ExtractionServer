3-1. 2의 유효성 검사가 올바르지 않은 경우, '귀환 응답' 프로토콜(D2CResponseRecall)에 false를 담아 응답한다.
3-2. 2의 유효성 검사가 올바른 경우, '귀환 응답' 프로토콜에 true와, 해당 '귀환 스팟 인덱스'를 담아 응답한다.

현재 C2DRequestRecall의 핸들러는 어떻게 구현되있지?

C2DRequestRecall의 핸들러에 다음 기능을 추가하려고 해.
1. 유효한 요청이어서 D2CResponseRecall로서 true의 응답을 보낸 경우 5초뒤에 귀환 요청을 처리하는 것을 목표로 함.
2. 1초 간격으로 해당 플레이어가 유효한 위치에 존재하는가를 확인, 유효하다면 다음 시퀀스를 진행하고, 시퀀스가 5가되면 귀환 처리.
3. 위의 경우에서 유효하지 않은 위치에 존재한것이 확인된 경우, 귀환 취소.
4. 귀환 처리와 귀환 취소는, D2CNoticeRecallResult 로서 true 혹은 false를 전송함으로서 플레이어에게 알림.
위의 계획에 대한 반론이 있을까?

1. 5초뒤 처리 타이머를 따로 둘 것은 아니었어. 5초 뒤의 귀환 요청을 처리하기 위해서, 1초 간격의 시퀀스를 5번 둔다는 뜻이었어.
2. 좋아, PlayerSession에 귀환 상태를 기록하는 것이 좋아보여.
3. nullptr문제가 발생할 수 있으니, 동의하는 부분이야.
4. 멱등성 있게 동작해야해. 진행중인 귀환이 있을 경우의 귀환 요청은 무시하도록 하겠어. 기존의 귀환 요청이 실패, 성공함에 따라서 서버에서 따로 응답을 줄테니 문제가 되지 않을 거라고 봐.
5. 피격시 취소할 생각은 없어. 다만, 죽은 플레이어와 DISCONNECTED여부는 검사하는 것이 좋아보여.
6. C2DUpdatePlayerState로서 클라이언트 주도로 갱신되는 값이 맞지만, 0.1초 간격으로 촘촘히 전송되는 패킷이기도 해. 부정한 움직임이 있다면 C2DUpdatePlayerState 혹은 지금 우리의 귀환로직이 아닌, 다른 곳에서 부정한 행위를 탐지하는 것이 구조적으로 맞다고 생각해.
7. 맞아. 정확히 5초가 아닐거야. 그래도 괜찮아.
8. 동의해.
9. 성공시에, 이 핸들러 함수 내에서 즉시 Session에 대한 작업을 진행하지 않을거야. 그것과는 별개로 일단 NotifyRecallResult만 전송하고 Session작업 및 결과를 DB에 반영하거나 하는 내용은 지금 진행하지 않고 TODO:의 주석으로만 적어두자.
