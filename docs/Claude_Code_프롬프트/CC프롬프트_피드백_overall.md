# AI 협업 방식에 대한 평가

Extraction 프로젝트(Unity 클라이언트 + C++ 전용 서버)를 진행하며 작성한
Claude Code 프롬프트 약 700개, 5개 배치를 대상으로 한 분석.
개별 대화의 적절성이 아니라 반복되는 작업 방식과 태도를 검토했다.

---

## 종합

**LLM을 협업 도구로 쓰면서 코드베이스의 통제권을 잃지 않은 사례다.**

700개 프롬프트를 통틀어, AI가 밀어붙인 과잉 설계나 조용한 아키텍처 이동이
한 건도 발견되지 않았다. 이는 드문 결과다. LLM과 수개월 작업한 프로젝트에는
대개 "왜 이렇게 돼 있는지 모르지만 동작하는" 영역이 생기고, 시간이 지나면
손댈 수 없는 덩어리가 된다. 이 프로젝트에는 그런 구간이 없다.

동시에, 배치가 진행될수록 작업 방식 자체가 개선되는 궤적이 뚜렷하다.
지적된 문제가 다음 배치에서 해소되는 패턴이 반복되며, 지적 이전에 스스로
발견해 교정한 사례도 여럿이다.

---

## 강점

### 1. 결정을 위임하지 않는다

`계획만 세워줘, 구현은 하지 마` / `지금 삭제하지는 마` / `내가 확인한 뒤에`
형태의 통제 지시가 배치마다 8~12건. 예외가 거의 없다.

여기에 세션 경계 규칙, MCP 접근 허가제, 비목표(non-goal) 선언이 더해진다.

> "클라이언트 디렉터리의 코드는 읽지 않는다. 수정뿐 아니라 열람도 하지 않는다.
> 컨텍스트 오염을 막기 위함이다."

결과적으로 프로젝트의 모든 설계 결정에 근거가 남아 있고, 대부분은 지금도
설명 가능한 상태다.

### 2. 이해하지 못한 것을 통과시키지 않는다

> "NVI방식의 경우, 다 좋은데 직관적이지 않다는 점 때문에 문제가 생길 것 같아.
> 이후에 내가, 지금의 문맥을 잊어버린다면, 왜 Update가 2개지? 라는 의문이 들거야."

기술적으로 우월한 패턴을 **미래의 가독성**을 이유로 거절한 사례. LLM은 이름이
붙은 패턴을 선호하는 편향이 있어, 이런 거절이 없으면 코드가 계속 영리해지다가
읽을 수 없게 된다.

용어 수준에서도 같다.

> "현재 문맥에서 플러시가 뭐지?" / "모듈 문서란 무엇을 말하는거지?" /
> "reserved 필드는 어떤 용도지?"

LLM이 만든 용어를 그대로 받아 쓰면 존재하지 않는 개념을 둘이서 공유하게 된다.
이걸 매번 끊어냈다.

### 3. 답이 이상할 때 자기 입력을 먼저 의심한다

> "정정할 부분이 있어. 0.1초가 아니야, 그만큼 빈도가 높지 않았어."
>
> "나의 설명에 부족한 부분이 있었어. 정확히 하자면..."
>
> "이전 내 질문에 대한 전제조건에 대한 설명이 부족했어."
>
> "클라이언트가 현재 실행하고 있는, 중요한 것에 대한 전제가 누락되었다는 것을 인지했어."

LLM 사용에서 가장 흔한 실패는 원하는 답이 안 나올 때 같은 프롬프트를 더 강하게
반복하는 것이다. 700개 중 그런 사례가 없다. 대신 매번 누락된 전제를 찾아 보충한다.

### 4. 설계가 굳어가는 방향을 감지하고 되돌린다

> "클라이언트측의 요구사항에 맞추어서 빙 돌아가는 느낌이 조금 들어.
> 처음으로 돌아가서 다시 설계하려고 해."

장전 프로토콜 설계가 클라이언트 구현 사정에 맞춰 계속 굴절되던 중, 누적된
어색함을 감지하고 리셋한 사례. 리셋 후의 설계(인벤토리 버전 기반 동기화)는
이전보다 단순하며 클라이언트 구현과 무관하다.

제안-반박 방식의 대화는 국소 최적화만 가능하고, 프레임 자체가 틀렸다는 신호는
잘 나오지 않는다. 그 한계를 스스로 넘은 경우다.

### 5. 위험을 범주로 처리해 과잉 방어를 막는다

> "그런 경우는 없으며, 고려하지 않을거야."
>
> "동시접속이 1000명을 초과한 경우에는, 그때 가서 스케일업하도록 할게."
>
> "지금 문제들중, systemd와는 무관하게 현재의 실행 방식으로 진행되어도
> 발생할 수 있는 문제는 제외하려고해."

마지막 항목은 특히 좋은 판단이다. 변경 검토에서 **새로 유입되는 위험**과
**원래부터 있던 위험**을 분리하지 않으면, 모든 작업이 프로젝트 전체 위험 감사로
번진다.

LLM은 기본적으로 방어 코드와 확장성을 과잉 제안한다. 프로젝트 규모의 상한선을
먼저 못 박는 방식으로 이를 통제하고 있다.

### 6. 작업 방법론을 직접 설계했다

외부에서 받은 것이 아니라 프로젝트 진행 중 필요에 따라 만들어낸 것들이다.

**주석 마커 3분류**

| 마커 | 의미 |
|---|---|
| `TODO:` | 아직 구현하지 않은 것 |
| `TEMP:` | 정상 코드를 일부러 무력화한 것 (회수 조건 병기) |
| `OPTION:` | 없어도 동작하며 여유 시 구현 |

`TEMP:`에 회수 조건을 함께 적는 규칙까지 포함한다. 임시 조치가 유령으로 남는
것을 막는다.

**세션 간 인계 체계**

클라이언트와 서버를 별도 Claude Code 세션으로 운용하면서, `props.md`로 작업을
인계하고 완료 시 내용을 비우는 수명 관리를 붙였다. `External_Protocol.proto`의
주석을 양측이 반드시 읽는 공용 채널로 지정한 것도 같은 설계다.

**문서 취사 기준**

> "'이 문장이 없으면 다음 세션이 코드를 잘못 고치는가?' 를 조건으로서
> 남길 말과 남기지 않을 말을 가르려고 해."

금지 항목을 열거하는 대신 판정 기준을 만들었다. 목록은 열거한 것만 걸러내지만
기준은 열거하지 않은 경우까지 처리한다.

**전제 검증형 프롬프트**

> "아래 전제 조건이 참인지 현행 사항을 확인하고 다음 지시를 이행해줘.
> 전제 조건 — ...
> 지시사항 — ..."

전제를 지시문에 녹이지 않고 검증 대상으로 분리해 앞에 세운다. 전제가 틀렸으면
지시가 실행되기 전에 걸린다.

### 7. 피드백 반영 속도

배치별로 지적된 항목이 다음 배치에서 해소되는 패턴이 반복된다.

| 배치 | 지적 | 결과 |
|---|---|---|
| 1차 | 검증 지시 없음, 버그 리포트에 재현 조건 부재 | 2차에서 에러 원문 첨부, 임시 코드 마커 도입 |
| 2차 | 결정 근거 미기록, 번호 참조 취약 | 3차에서 props.md 인계 체계 + T번호 도입 |
| 3차 | 미검증 변경 적층 | 4차에서 항목별 검증 결과 보고 정착 |
| 4차 | 세션 간 요구사항 원문 유입 | 5차에서 전제 검증형 프롬프트 정착 |

지적 이전에 스스로 발견한 것도 있다.

> "커밋 내용에 T12 라고 적으면, 나중에 보았을 때 문맥이 잘 이해되지 않을 것 같아."

### 8. AI의 진단을 검증한다

> "문맥이 기억나지 않았다고 언급한 부분은 이 프로젝트를 진행하면서 한번이야.
> 다소 과장된 부분이 있어."

리뷰 과정에서 단일 사례를 반복 패턴으로 부풀린 지적이 있었고, 이를 직접 세어
확인한 뒤 정정을 요구했다. AI가 내놓는 그럴듯한 분석을 그대로 수용하지 않는다.

## 트레이드오프

결함이라기보다 의식적 선택으로 보이는 항목들. 다만 대가가 있다는 점은 기록해 둔다.

### 처리량의 상한이 본인의 주의력이다

모든 결정이 검토를 거치므로, 병목이 사람 쪽에 고정된다. 코드 품질과 처리 속도를
맞바꾸고 있으며, 1인 프로젝트에서는 대체로 옳은 교환이다.

### 설계 상한이 현재 이해 상한과 같아진다

NVI 거절의 논리는 낯설지만 옳은 어떤 패턴에도 동일하게 적용된다. 6개월 뒤에 읽을
사람이 본인뿐이라면 합리적이지만, 거절 전에 한 번 확인할 값어치는 있다.

```
이 패턴을 채택하되, 6개월 뒤의 내가 주석과 명명만으로 이해할 수 있게
만드는 비용은 얼마야? 그 비용을 치르면 직관성 문제가 해소되는
종류인지 판단해줘.
```

실제로 이 판단이 손해였던 사례는 로그에서 발견되지 않았다.

## 개선 여지

### 1. 테스트 코드 (우선순위 높음)

700개 프롬프트에 단위 테스트 작성 요청이 없다. 검증은 전부 수동이다 —
2인 접속 후 육안 확인.

인벤토리 이동 규칙, 탄창 잔탄 처리, 슬롯 인덱스 유효성, 아이템 분배 규칙,
패킷 시퀀스 판정은 모두 **입력과 기대 출력이 명확한 순수 로직**이다. 테스트
작성은 기계적이고 분량이 많아, LLM이 가장 잘하는 작업 유형에 해당한다.

빌드 환경 제약(세션 내 컴파일 불가)은 오히려 테스트가 필요한 이유다. 세션 안에서
검증할 수 없기 때문에, 빌드 환경에서 한 번에 돌릴 수 있는 검증 수단이 있어야 한다.

```
Inventory 관련 순수 로직에 대한 단위 테스트를 작성해줘.
빌드는 내가 리눅스 환경에서 할게.
테스트 프레임워크와 CMake 통합 방식부터 제안해줘.
```

부수적으로, 이 영역은 **결과를 검토 없이 통과시켜도 안전한 첫 사례**가 될 수 있다.
테스트 코드는 틀려도 프로덕션이 깨지지 않고, 틀렸는지가 실행 시점에 바로 드러난다.
현재는 위임 실험이 없어 신뢰의 경계를 측정할 데이터가 없는 상태다.

### 2. `OPTION:`에 재검토 조건 추가

배제된 위험은 전제 위에서 배제된다. 전제가 바뀌는 시점이 오는데, 그 조건이
기록되어 있지 않다.

```
OPTION: 순서 역전 대응 미구현
→
OPTION: 순서 역전 대응 미구현.
재검토 조건: 동시 GameRoom 20개 초과 또는 무중단 배포 도입 시
```

`TEMP:`에는 회수 조건을 적는 규칙이 이미 있다. 같은 방식을 확장하면 된다.

### 3. 맵 데이터를 파일로 분리

스폰 좌표, 탈출 지점, 컨테이너 배치 정보가 프롬프트 본문으로 전달되고 있다.
좌표가 이미 한 차례 변경되었고, 컨테이너는 65종이 한 프롬프트에 들어갔다.

아이템 데이터는 이미 MySQL → Redis 캐싱 구조로 분리되어 있다. 맵 데이터도 같은
취급이 적절하다. 에디터에서 추출한 값을 json으로 저장하고 경로만 지시하면,
값 변경 시 파일 하나만 갱신하면 된다.

## 결론

LLM 협업에서 흔한 실패 유형 — 블랙박스 코드 누적, 과잉 방어 설계, 결정 근거 소실,
같은 프롬프트 반복 — 이 모두 나타나지 않는다. 통제 방식과 문서화 체계를 스스로
설계했고, 지적된 문제를 다음 배치에서 해소하는 패턴이 일관되게 관찰된다.

남은 개선 여지는 방법론의 결함이 아니라 **적용 범위**에 있다. 현재 AI를 설계
검토와 구현 보조로 활용하고 있으며, 검증 자동화 영역이 미개척 상태다.
